## 优化盘点（只读审查，未改代码）
实测与代码核查得出的可优化项，按优先级：

### P0 体验
1. **封面 N+1 请求且无缓存**：GD 搜索结果只有 `pic_id`，没有图 URL，所以每行 `SongCover` 都要再发一次 `types=pic`。实测该接口不稳定：三次分别 503(1.4s) / 200(2.4s) / 000(15s 超时)。榜单详情页一次渲染 **100 行 = 100 个并发请求**；首页 20 行/页。缺统一缓存层（`apiService` 无 cache，只有 `playUrlResolver` 有 Map 缓存）。修法：`services/picCache.js` 做内存 LRU + 并发限流(4~6) + 失败快速降级。
2. **长列表没做窗口化**：`RankingDetailScreen` 用 `ScrollView + map` 一次性渲染 100 行，改 FlatList（initialNumToRender / windowSize / removeClippedSubviews）。
3. **推荐页占位图依赖 picsum.photos**：实测国内 HTTP 000（15s 超时）→ 全是空白方块。且「最近常听」是硬编码 `歌曲A..F`，而 `libraryStore.recent` 里本来就有真实数据可接。

### P1 一致性
4. `services/downloadService.js` 下载固定 `128k` 且文件名恒 `.mp3`：播放页选无损后下载仍是 128k，FLAC 会被写成 .mp3。
5. `playerStore` 队列与进度共用一个持久化 key，每 4s 整包写盘。
6. 播放页仍按 500ms 粒度整体重渲染（下一步可把进度条+时间抽成子组件，`useMemo` 已做唱片/歌词）。
7. `apiService.getToplistDetail` 仍是 `Promise.resolve({list:[]})` → 首页「云端排行榜」长期靠 demo fallback。

### P2 清理
8. `screens/SimpleScreen.js` 零引用，死文件。
9. `RankingDetailScreen` 头部「280.3万 / 15.8万 / 14021」是硬编码假数字。
10. `services/logFilters.js` 全局静音告警，建议限定只在 Expo Go 调试模式生效，避免掩盖真实报错。
11. `.gitignore` 已屏蔽 `dist/ build/ *.apk`，仓库无产物膨胀问题。

- **隐藏面板不发请求**：RecommendScreen 常驻挂载但不可见，其 9 个请求（轮播 1 + 8 歌单封面）改为切到「推荐」才发。
- **补页请求延后**：`getMoreDailySongs`（6 个请求）改为翻到第 6 页才触发，快速批次 4×30 首已覆盖前 6 页。

## 23:20 四轮手机实测验证网络优化（探针方式，事后已移除）
- 方法：临时在 apiService.gd / picCache 加 `global.__NET_PROBE__` 日志，Metro 日志里计数（日志 `%TEMP%/musicapp-expo/expo-out.log`）。
- 实测结论：
  - 启动请求 4 个 ✓（推荐页 9 个请求只在切到「推荐」时才发，隐藏时的 11 次封面记录 key 为空、属空跑 0 流量）
  - 「翻到第 6 页才补数据」✓
  - 封面尺寸：120px 151 次 / 250px 23 次 / 500px 12 次 ✓
  - 落盘机制可用：存到 102 条、启动时确实读到 12271 字节 ✓ **但跨启动命中率为 0**
- 命中率 0 的三个根因（逐个排除）：
  1. 推荐关键词游标每次调用 +1 → 每次启动不同关键词（已改为按天固定，下拉刷新才推进）
  2. 结果列表用 Math.random() 洗牌 → 上游其实确定（同关键词三次请求 id 完全一致，md5 相同），唯一变量是自家洗牌（已改为按天种子可复现的 seededShuffle）
  3. 上游约一半请求返回空响应（不是报错/超时）→ 首页少一批歌（已加「仅对空响应」补问一次，不违反超时不重试原则）
- 教训：上游 `types=pic` 慢（8s abort）且常空返回，是封面链路的天花板；磁盘缓存能省流量，但受上游可靠性制约。
